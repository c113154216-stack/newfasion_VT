# 3Dclothes_project 程式碼詳細說明

這份文件逐檔案、逐函式解釋 `3Dclothes_project/` 的程式碼在做什麼、為什麼這樣寫、彼此怎麼串起來。
寫這份文件的方法是**實際讀過每一支 `.py` 檔案**（不是憑檔名猜),並且拿掉環境裡已經跑起來驗證過的
真實結果來對照(例如哪些路徑實測過、哪些只是讀程式碼推論)。跟先前那份
`程式碼註解狀況與說明.md` 的差異是:那份重點是「哪裡有沒有註解」,這份是「完整技術說明」,
就算原始程式碼沒註解,這裡也會補上白話解釋。

---

## 1. 技術棧

| 分類 | 技術 |
|---|---|
| 後端框架 | Flask 3 + flask-cors |
| ORM / DB | SQLAlchemy 2(宣告式 Mapped 語法)+ PyMySQL,資料庫是 MySQL/MariaDB(XAMPP) |
| 向量檢索 | FAISS(`IndexFlatL2`) |
| 影像/文字編碼 | FashionCLIP(`Marqo/marqo-fashionCLIP`,透過 `open_clip` 載入) |
| 穿搭推薦模型 | 自製 Transformer(`outfit_transformer/model.py`,複現 Sarkar et al. WACV 2023) |
| 人體生成 | SMPL-X(`smplx` 套件 + 官方權重) |
| 服裝幾何 | 自製參數化網格生成(`geometry_physics/geometry_engine.py`) |
| 3D 檔案格式 | glTF Binary(`.glb`),用 `trimesh` 讀寫 |
| 前端 3D 渲染 | Three.js(CDN `unpkg.com`,不是 npm 套件) |
| 測試 | pytest,搭配環境變數 `PYTEST_CURRENT_TEST` 觸發全套 mock |

## 2. 整體架構:三個人的三塊、一個共同的膠水層

```
                        ┌─────────────────────┐
                        │       app.py         │  Flask 進入點
                        └──────────┬───────────┘
                                   │ 註冊 Blueprint
              ┌────────────────────┴────────────────────┐
              │                                          │
   ┌──────────▼───────────┐                 ┌────────────▼─────────────┐
   │ module1_pipeline/     │                 │ module_integration/       │
   │ routes.py             │                 │ routes.py                 │
   │ (商品上架/檢索/找搭配)  │                 │ (3D 試穿模擬)              │
   └──────────┬───────────┘                 └────────────┬─────────────┘
              │                                           │
   ┌──────────▼───────────┐                 ┌────────────▼─────────────┐
   │ product_service.py    │                 │ orchestrator.py           │
   │ - upload_product()    │                 │ run_tryon_simulation()    │
   │ - recommend_products()│                 │  M2 → M3 → M4 依序呼叫    │
   └──────────┬───────────┘                 └────────────┬─────────────┘
              │                                           │
   ┌──────────▼─────────────────────────────────────────▼─────────────┐
   │                          adapters/ (固定介面)                       │
   │  fashionclip_adapter.encode()      ← 林宇鑫 M1                      │
   │  outfit_transformer_adapter.find_complementary()  ← 林宇鑫 M1       │
   │  body_generator.generate()         ← 紀泓宇 M2                      │
   │  garment_processor.prepare()       ← 紀泓宇 M3                      │
   │  physics_simulator.run()           ← 紀泓宇 M4                      │
   └──────────────────────────────────────────────────────────────────┘
              │                                           │
   ┌──────────▼───────────┐                 ┌────────────▼─────────────┐
   │ services/vector_store │                 │ geometry_physics/          │
   │ (FAISS 封裝)           │                 │ body_model.py (SMPL-X)     │
   │                        │                 │ geometry_engine.py (服裝) │
   └────────────────────────┘                 └───────────────────────────┘
              │                                           │
   ┌──────────▼─────────────────────────────────────────▼─────────────┐
   │                     database/models.py (MySQL,共用)                 │
   │   Product / BodyProfile / TryOnSession / Outfit / OutfitItem       │
   └──────────────────────────────────────────────────────────────────┘
```

**核心設計原則**:`adapters/` 是三個人程式碼之間唯一的邊界。`module1_pipeline/` 跟
`module_integration/` 兩層業務邏輯**只呼叫 adapter 提供的固定函式簽章**,完全不直接
`import geometry_physics` 或 `import outfit_transformer`。這樣任何一個人改自己模組內部的
實作,只要 adapter 對外的函式簽章不變,其他人的程式碼完全不用動。

## 4. 資料庫 Schema(`database/models.py`)

五張表,SQLAlchemy 2 的 `Mapped[]` 宣告式語法:

### `Product`(商品)
| 欄位 | 型別 | 說明 |
|---|---|---|
| id | PK | |
| name | str | 商品名稱 |
| description | str? | |
| category | str,有 index | `top` / `bottom` / `outer` / `dress` 等,找搭配時用來篩選候選池 |
| size_chart | JSON? | `{"S": {...}, "M": {...}, "L": {...}}`,`garment_processor` 用來算尺寸縮放比例 |
| image_path | str? | 本機檔案路徑 |
| garment_template_id | str? | 對應 `garment_processor.GARMENT_TEMPLATES` 裡的公版服裝 key |
| faiss_vector_id | int?,有 index | 這件商品的向量在 FAISS index 裡的位置 |
| status | str | `active` / 下架,查詢一律過濾 `status="active"` |
| created_at | datetime | |

### `BodyProfile`(身形)
`height_cm` / `chest_cm` / `waist_cm` / `hip_cm`,每次試穿都會新建一筆(不是使用者帳號綁定的
長期資料,單純是這次試穿請求的身形快照)。

### `TryOnSession`(試穿紀錄)
關聯 `Product` + `BodyProfile`,存 `body_glb_path`(M2 輸出)、`result_glb_path`(M4 最終輸出)、
`status`(`processing` → `done`/`failed`)、`error_message`。

### `Outfit` / `OutfitItem`(穿搭組合,給 OutfitTransformer 訓練用)
- `Outfit.source`:`"polyvore"`(借來的訓練資料)或 `"shop"`(真實商家穿搭),**同一張表混著存**
- `Outfit.split`:`train`/`valid`/`test`,保留 Polyvore 原始切分,確保訓練不會洩漏到評估集
- `OutfitItem.product_id` 跟 `external_item_id` 互斥:真實商品填前者,Polyvore 借來的商品填後者
- `outfit_items.outfit_id` 設 `ON DELETE CASCADE`——刻意設計成這樣,是為了讓
  `DELETE FROM outfits WHERE source='polyvore'` 這種指令能一次乾淨清掉所有借來的訓練資料,
  不會動到真實商家資料,也不用另外寫清理程式

## 5. `adapters/` 逐檔詳解(三人邊界層)

### 5.1 `fashionclip_adapter.py` — 林宇鑫 M1
唯一對外函式:`encode(image_path=None, text=None) -> np.ndarray(512,)`

- 只給圖 → 圖片向量;只給文字 → 文字向量;兩個都給 → **兩個向量先各自 normalize 再相加除以 2,
  再整體 normalize 一次**(不是簡單平均),用來模擬 GCL 論文的 multi-field 概念,讓「有圖又有名稱」
  的商品編碼同時吃到兩種資訊。
- 惰性載入:第一次呼叫才真的 `open_clip.create_model_and_transforms()` 把模型讀進記憶體,
  用全域變數 `_model` 快取,之後呼叫直接跳過。
- **雙重 mock 判斷**:`PYTEST_CURRENT_TEST` 有值,或 `open_clip`/`torch` 沒裝(`_HAS_FASHIONCLIP=False`)
  → 都會改用 `_mock_encode()`。這支 mock 是用文字內容的 hash 當隨機種子生成單位向量,**同樣輸入
  永遠得到同樣的假向量**,讓測試結果可重現。
- 有一個維度檢查:輸出如果不是 `Config.FAISS_VECTOR_DIM`(預設 512)會直接丟例外,避免不小心
  換了模型架構卻沒發現向量維度變了。

### 5.2 `outfit_transformer_adapter.py` — 林宇鑫 M1
唯一對外函式:`find_complementary(product_ids, target_category, top_k=5) -> list[dict]`

完整推論流程(7 步驟,程式碼本身已有詳細註解,這裡摘要):
1. 把 `product_ids` 轉成 DB 裡的 `Product` 物件
2. 每件已選商品用 `fashionclip_adapter.encode(image, name)` 編碼成向量,當作「部分穿搭」
3. 從 DB 撈出同 `target_category`、`status="active"`、且不在已選清單裡的候選商品
4. 組成模型輸入:`vectors_t (1, N, 512)` + `mask_t (1, N)`(單一請求不需要 padding)
5. `target_category` 文字先過 FashionCLIP 編碼成 `target_spec`,結果快取在 `_category_cache`
6. 跑 `model.target_item_embedding()`,輸出**手動 normalize**(模型輸出本身沒內建 normalize,
   長度跟 FashionCLIP 向量的 1.0 對不上,不補的話會讓所有距離被系統性拉大、失去鑑別度)
7. 跟每個候選商品的 FashionCLIP 向量算 cosine similarity(兩邊都是單位向量,內積即 cosine),
   排序後把 `-1~1` 映射到 `0~1` 回傳

**檢查點(已用真實 checkpoint 實測過)**:2026-08-26 用 `cir_model.pt` 實際跑過
`find_complementary(product_ids=[1], target_category="bottom")`,8.74 秒回傳合理排序的結果
(分數 0.55~0.56 區間有鑑別度)。模型權重是隊友自己訓練好、直接 commit 進 git 的(5.5MB,
`data/polyvore_cache/checkpoints/cir_model.pt`),不需要重新訓練。

跟上游 `jackzhao30/3Dclothes_project` 比對:這支檔案在我們這份多了一個**真正的 bug 修正**——
上游算分數用 `1/(1+distance)`(下限卡在 0.2,鑑別度差),我們這份改成正確的 cosine similarity
換算,不只是加註解而已。

### 5.3 `body_generator.py` — 紀泓宇 M2
唯一對外函式:`generate(height_cm, chest_cm, waist_cm, hip_cm, output_name) -> {"glb_path": str}`

- `_use_stub()` 只檢查 `PYTEST_CURRENT_TEST`,不檢查權重存不存在——這代表**正常執行(不透過
  pytest)一定會嘗試真實 SMPL-X 生成**,只有中途真的出錯(權重不存在、`smplx`/`trimesh` 沒裝等)
  才會 fallback 回 `_stub_generate()`(複製一個固定的 sample body glb)。
- 真實路徑呼叫 `body_model.smplx_body_from_measurements()`,把 (height, bust, waist, hip)
  這四個量測值反推成 SMPL-X 的 `betas` 形狀係數,再產生對應的人體網格。

**已實測**:補上 SMPL-X 權重(`geometry_physics/assets/smplx/SMPLX_{NEUTRAL,MALE,FEMALE}.npz`)
後,`tests/test_body_model.py` 裡原本 6 個 `SKIPPED` 的真實 SMPL-X 測試全部轉 `PASSED`。

### 5.4 `garment_processor.py` — 紀泓宇 M3
唯一對外函式:`prepare(product_id, size="M") -> {"glb_path": str}`

- `GARMENT_TEMPLATES` 是一個字典,把商品的 `garment_template_id`(例如 `"tshirt_base.glb"`)
  對應到實際的公版 obj 檔名 + 是否有袖子。目前 10 種樣板全部對應到 4 個實體 obj 檔
  (`tshirt_base.obj`、`shirt_base.obj`、`coat_base.obj`、`pants_base.obj`、`shorts_base.obj`),
  等於很多不同的服裝分類目前共用同一份幾何樣板,只是縮放參數不同。
- 有袖子的樣板走 `_load_base()` → `geometry_engine.build_real_shirt_template()` 或
  `build_base_shirt()`,拿到帶「混合權重」的公版網格,再依商品 `size_chart` 算出縮放參數丟進
  `geometry_engine.deform_vertices()`。
- 沒袖子(褲子/短褲類)走 `_load_static()`,直接讀 obj,不做尺寸變形(目前設計上褲裝沒有
  依尺寸表縮放的邏輯)。
- `_size_to_params()`:拿 size_chart 裡目標尺寸跟 `M` 尺碼的比例,換算成
  `{length, shoulder, chest, waist}` 這組縮放百分比(以 100 為原尺寸)。
- 輸出時額外存一個「側車檔」(`.glb.json`,見 5.6 節)記錄 `has_sleeve_topology`,讓 M4
  知道要用哪種貼合邏輯。

### 5.5 `physics_simulator.py` — 紀泓宇 M4
唯一對外函式:`run(body_glb, garment_glb, output_name) -> {"glb_path": str}`

**注意:檔名叫 physics_simulator,但內部完全是幾何運算,不是真的布料碰撞物理模擬**——
這是團隊文件裡明講的已知簡化,不是我誤判。

真實路徑:
1. 讀回 body/garment 的 `.glb` 跟各自的側車檔(`load_sidecar`)
2. 從 body 側車檔拿到生成人體時用的 `betas`/`gender`/`pose`
3. 如果服裝有袖子拓樸:先 `bm.fit_garment_to_body()`(依身形調整服裝網格),
   再 `bm.pose_garment()`(把服裝蒙皮貼合到指定姿勢)
4. 沒袖子(褲裝):跳過 fit,只做 `pose_garment()`
5. 用 `trimesh.Scene()` 把 body + garment 兩個網格組成一個場景,匯出成最終 `.glb`

**已端到端實測**:2026-08-26 直接呼叫 `orchestrator.run_tryon_simulation(product_id=3, ...)`,
11.25 秒完成,`status="done"`,輸出 `1_body.glb`(377KB)+ `1.glb`(545KB)——檔案大小遠超過
stub 產生的 400 bytes 佔位檔,證實是真實幾何運算的結果,不是 mock。

### 5.6 `glb_utils.py` / `mesh_glb.py` — 共用的 GLB 工具
- `glb_utils.create_minimal_glb()`:純手刻二進位 glTF 格式(沒有依賴 trimesh),生成一個
  「可以真的在瀏覽器被 Three.js 讀取、旋轉觀看」的最小方塊網格,給三個 stub 函式共用當佔位輸出。
  這樣即使全走 mock,前端 3D 檢視器測試起來也不會拿到空白/壞掉的檔案。
- `mesh_glb.py`:用 `trimesh` 包裝的 `export_glb()` / `load_glb()`,加上**「側車檔」機制**——
  GLB 格式本身沒有欄位可以存 SMPL-X 的 `betas`,但 M4 貼合服裝時需要知道人體是用哪組 betas
  生成的,所以額外存一個同名 `.json` 檔(例如 `1_body.glb.json`)夾帶這些中繼資訊,
  `save_sidecar()` / `load_sidecar()` 一組讀寫函式。

## 6. `module1_pipeline/`(商品上架、檢索、找搭配 API)

### `product_service.py`
- `upload_product()`:存商品圖 → `fashionclip_adapter.encode()` → `vector_store.add_vector()`
  → 寫入 DB。**失敗處理是手動維持一致性,不是資料庫 transaction**:任何一步出錯就
  `db.rollback()` 並且手動刪掉已經存到硬碟的圖片檔——因為 FAISS index 跟 MySQL 是兩個獨立的
  儲存系統,沒有辦法用同一個 transaction 保護。
- `recommend_products()`:文字/圖片查詢 → FAISS 搜尋 → 依 `faiss_vector_id` 反查 DB 商品。
  距離換算成分數的公式有詳細註解:FAISS `IndexFlatL2` 回傳「平方 L2 距離」,兩個單位向量的
  平方 L2 距離範圍是 0~4(對應 cosine similarity 的 -1~1,關係式 `squared_L2 = 2 - 2*cosine`),
  所以用 `1 - squared_L2/4` 換算回 cosine 再映射到 0~1,比原本上游版本的 `1/(1+distance)`
  更準確反映真實相似度(已實測:查 `"a red t-shirt"` 回傳結果最像的是白色 T 恤,分數 0.7316)。

### `routes.py`(Blueprint 掛在 `/api` 前綴)
| 路由 | 方法 | 說明 |
|---|---|---|
| `/api/health` | GET | 健康檢查 |
| `/api/products/upload` | POST | 上架商品(multipart,含圖片檔) |
| `/api/products/<id>` | GET | 單一商品詳情 |
| `/api/products` | GET | 商品列表(`limit` 上限鎖 500,避免被打爆) |
| `/api/outfit/complete` | POST | 找搭配,呼叫 `outfit_transformer_adapter`(延遲 import,避免沒用到這支 API 也要付 PyTorch 模型載入成本) |
| `/api/recommend` | POST | 以文字/圖片找相似商品 |

## 7. `module_integration/`(試穿流程)

### `orchestrator.py`
- `validate_body()`:檢查四個身形欄位存在、能轉成 float、且落在 `BODY_RANGES` 合理範圍內
  (身高 140~220cm、胸圍 60~150cm、腰圍 50~140cm、臀圍 60~160cm)。
- `run_tryon_simulation()`:整個 3D 試穿的骨幹,依序 M2 → M3 → M4:
  1. 查商品、驗證身形
  2. 建 `BodyProfile` + `TryOnSession`(初始 status=`processing`)
  3. `body_generator.generate()` → 人體 glb
  4. `garment_processor.prepare()` → 服裝 glb
  5. `physics_simulator.run()` → 合成最終 glb
  6. 任何一步丟例外 → `status="failed"` + 記錄 `error_message`;全部成功 → `status="done"`
  7. `_elapsed_seconds` 是塞進 session 物件的臨時屬性(不是 DB 欄位),純粹給 API 回傳耗時參考用

**已端到端實測**(見 5.5 節),全程真實執行,非 mock。

### `routes.py`
| 路由 | 方法 | 說明 |
|---|---|---|

| `/api/tryon/simulate` | POST | 觸發試穿模擬,回傳 session_id + 3D 模型 URL |
| `/api/tryon/status/<id>` | GET | 查詢試穿狀態(目前是同步阻塞執行,這支是為了以後改非同步/Celery 預留的介面) |

## 8. `services/`

- `vector_store.py`:`VectorStore` 類別包住 `faiss.IndexFlatL2`。`add_vector()` 回傳新向量在
  index 裡的位置當 id;`persist=False` 可以跳過每加一筆就寫一次硬碟,批次匯入時自己控制何時
  `save()`。全域單例模式(`get_vector_store()`),第一次呼叫才真正 load-or-create index 檔案。
- `response.py`:統一 API 回應格式,`success_response()` 包 `{"success": true, "data": ...}`,
  `error_response()` 包 `{"success": false, "error": "..."}`。

## 9. `geometry_physics/`(紀泓宇的幾何運算核心)

### `geometry_engine.py` — 服裝樣板生成與變形
公版短袖上衣用兩塊組成:
- **軀幹**:用「輪廓內插(smoothstep,不是線性內插,避免明顯折角)+ 旋轉延伸(lathe)」建立
  橢圓截面的中空管狀網格,寬度沿高度依控制點(下擺/腰/胸/肩)內插,領口用 `_apply_neckline()`
  在肩線頂端前後中心挖出 U 型凹陷。
- **袖子**:各自獨立建模成一根從肩點朝外、略微下垂的中空圓管,用 Rodrigues 旋轉矩陣把局部座標
  對齊到肩袖方向後接上軀幹。

尺寸調整不是逐頂點純量縮放,是簡化版的 **Linear Blend Skinning(LBS)**:每個頂點在建網格
當下就依所屬部位(base/shoulder/chest/waist)算好混合權重(四個權重相加恆為 1),縮放時
每個部位各自套用一個 4x4 齊次縮放矩陣,最終頂點是這幾個變形結果的加權混合——跟 SMPL-X
用權重混合多個骨骼變換矩陣的概念一致,方便以後直接換成真正的骨骼權重。

`build_real_shirt_template()` 額外處理外部真實服飾掃描網格(例如 MGN Multi-Garment 資料集):
自動判斷哪些頂點是「袖子」——下半身(t<0.5)橫向延伸必定不含袖子,拿它的最大橫向延伸當基準,
超過基準 1.15 倍的頂點視為袖子,比單純按高度切一刀準確,能避免調整「肩寬」時把領口也一起撐開。

### `body_model.py` — SMPL-X 相關(581 行,本身註解密度最高的檔案之一)
主要函式(依 `grep def` 列出的簽章推斷用途):
- `build_proxy_mannequin()`:**純幾何的替代人偶**,不需要 SMPL-X 權重就能測試「對齊」邏輯本身
  對不對,這是 CLAUDE.md 提過的「權重就緒前的開發手段」。
- `fit_betas_to_measurements()` / `smplx_body_from_measurements()`:把 (身高/胸/腰/臀) 這組
  量測值反推成 SMPL-X 的 `betas`,再產生對應姿勢的人體網格。
- `fit_garment_to_body()` / `pose_garment()`:把服裝網格依身形調整、貼合到指定姿勢。
- `measure_body_cm()` / `_band_girth_cm()`:反向操作——給定 `betas`,量出對應的身體圍度(cm),
  用來驗證「輸入的量測值」跟「SMPL-X 生成出來的人體」是不是真的吻合。
- `get_smplx_model()`:模型快取(`_SMPLX_MODEL_CACHE`),避免每次呼叫都重新從硬碟讀 108MB 的
  `.npz`(註解裡提到實測約 630ms,量大會很慢)。
- `align_body_to_garment()`:對齊邏輯本體,是 `build_proxy_mannequin()` 存在的目的——先用假人
  驗證這個函式對不對,權重到位後直接換真人體,對齊邏輯不用改。

## 10. `outfit_transformer/`(林宇鑫的推薦模型:訓練/評估/資料處理)

### `model.py` — 模型架構(Sarkar et al. WACV 2023 複現)
`OutfitTransformer`:輸入 512 維 FashionCLIP 向量投影到 128 維(跟論文的 128 維一致,故意設小,
6 層 16 頭在這維度下運算量很小)。跟論文的差異:論文自己訓練 ResNet-18(圖) + SentenceBERT(文字)
共 128 維的 item embedding,我們直接重用已有的 FashionCLIP,不用另外訓練 encoder。

兩個任務頭:
- **CP(相容性預測)**:`outfit_token`(可學習參數,代表整套穿搭)過 Transformer 後接一個線性層
  輸出一個 logit,是不是「合搭」的二分類。
- **CIR(互補商品檢索)**:`target_token_proj` 把「目標商品規格」(類別文字的 FashionCLIP 向量)
  投影當 token,輸出頭刻意輸出回 512 維(跟 FashionCLIP 同一個向量空間),這樣訓練完可以直接
  丟進現有的 `services/vector_store.py` 做 FAISS 搜尋,不需要另開一個索引。

刻意**沒有加位置編碼**——因為「一套穿搭」是無序集合,這對應論文說的排列不變性,不是漏加。

### `losses.py` — Set-wise Outfit Ranking Loss(論文公式 3)
`L = L_All + L_Hard`:
- `L_All`:目標向量到正解的距離,要比到「每一個」負樣本的距離都近(加 margin 的 hinge loss),
  對所有負樣本取平均
- `L_Hard`:只跟「最像正解的那個負樣本」(距離最小的困難負樣本)比較,逼模型連最難分辨的情況
  都要學會

margin 用論文的 2.0。

### `dataset.py` — 資料組裝
- `ItemEmbeddingStore`:包住 `encode_polyvore_items.py` 產生的 `.npz` 快取,`item_id -> 向量`
  的 O(1) 查詢。
- `load_train_outfits()`:從 DB 撈某個 split 的所有穿搭。**特意用兩次查詢**(先撈 outfit id,
  再分批用 `IN (...)` 撈全部 outfit_items)而不是 ORM 的 lazy-load relationship——避免 N+1
  query 問題,穿搭數量一多(這裡是六萬多筆)會非常慢。
- `build_position_lookup()`:`compatibility_train.txt` / FITB json 裡的商品是用
  `"{set_id}_{position}"` 字串表示,不是直接給 item_id,靠這個對照表翻譯回真正商品 id。
- `sample_negatives()`:同分類抽負樣本,排除掉「跟正解同一套穿搭」的商品——避免負樣本其實
  跟目標穿搭相容,污染訓練訊號。

### `train.py` — 訓練腳本(先 CP 打底,CIR 微調)
跟論文的三個刻意簡化(程式碼開頭已列清楚):
1. CP 用標準 `BCEWithLogitsLoss`,不是論文處理正負不平衡用的 focal loss
2. CIR 負樣本抽樣只做論文的「第一階段」(同粗分類抽),沒做「第二階段」細分類抽樣
   (因為 DB 只快取了粗分類 `semantic_category`)
3. Learning rate 用 1e-4 不是論文的 1e-5——因為論文端對端微調預訓練 ResNet18,我們的
   FashionCLIP 向量是凍結的,只訓練一個小 Transformer,可以吃比較高的學習率

`--smoke-test` 模式:只跑 3 個 batch、1 個 epoch,而且**存到不同的檔名**
(`cp_model.smoketest.pt`),註解直接寫出這是修過的 bug——「之前發生過一次沒做這個區隔,
把訓練了 68.5 分鐘的真實權重蓋掉」。

### `evaluate.py` — 正式 FITB 評估
用官方 `fill_in_blank_test.json` 考題(4 選 1,answers[0] 固定是正解),**全部用 test split**
(模型訓練時沒看過),算出來的準確率才能跟論文報的數字(disjoint 59.48% / non-disjoint 67.10%)
放在同一基準比較。程式裡有結構性驗證(`correct_set_id != question_set_id` 就跳過)確保
「正解永遠是 index 0」這個假設沒有被破壞,不是憑空假設。

### `encode_polyvore_items.py` — 批次編碼快取
把 Polyvore 圖片跑過 FashionCLIP,存成 `item_id -> 512維向量` 的 `.npz` 快取。支援
`--split {train,valid,test}` 分開跑,設計成可以無人值守執行:每處理完一批印進度到 log、
每 200 批存一次中間結果(斷點續傳)、任何例外都會被捕捉並記錄不會讓 process 憑空消失、
跑完寫一個 `.DONE` 標記檔方便隔天確認到底跑完了沒。

## 12. 已知問題/限制(不是環境設定沒弄好,是程式碼本身的已知狀況)

1. **`/` 正式首頁 bug**:`web/index.html` 內容其實還是 `/dev` 測試頁的複製,沒有真的改寫成
   「服飾檢索」簡化版,`tests/test_health.py::test_product_and_dev_pages` 會 fail。
2. **M4 不是真物理模擬**:模組名稱叫 physics_simulator,實際是幾何貼合,不是布料碰撞模擬。
3. **OutfitTransformer 訓練是簡化版**:見第 10 節的三個差異點,已知會影響精度但目前
   FITB 67.44% 沒有比論文的 67.10% 差,簡化沒有傷到主要指標。
4. **試穿是同步阻塞執行**:`/api/tryon/simulate` 目前直接在請求裡跑完整個 M2→M3→M4,
   `/api/tryon/status/<id>` 這支輪詢 API 是為了以後改非同步/Celery 預留的介面,現在還用不到。
5. **Three.js 走 CDN**:`unpkg.com` 沒有 vendor 進專案,CDN 打不到時前端 3D 檢視器會靜默失敗
   (後端 API 其實有成功,只是畫面出不來)。
6. **MySQL 非服務化**:XAMPP 的 `mysqld.exe` 不是註冊成自動啟動服務,每次要手動啟動。
