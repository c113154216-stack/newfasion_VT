# UV 貼圖 — 這兩天做了什麼（詳細工作記錄）

**用途**：交接給另一台裝置的 AI，讓它不用重新問一輪就能接續 UV 貼圖這條工作線。
內容按時間順序，記錄「做了什麼、為什麼這樣做、遇到什麼問題、怎麼解決」。

**背景一句話**：目標是把商品照片「印」到 3D 服裝模型表面上，取代現在整件服裝塗單一顏色的做法。
這是全新要補的能力——現有 `geometry_engine.py` / `mesh_glb.py` 完全沒有 UV/材質貼圖機制。

---

## 第一天：搞懂概念 + 規劃最小驗證範圍

### 1. 起因

盤點下一步規劃「擴充真實服裝掃描」時，對照一份「3D 服飾公版模型庫」規劃書跟現有程式碼，
發現兩個落差最大的技術缺口，其中一個就是 UV 貼圖——現有服裝生成完全是程序化數學公式
（`geometry_engine.py` 用輪廓內插+旋轉延伸算軀幹形狀），從頭到尾沒有任何「把照片貼到表面上」
的機制，唯一跟顏色有關的程式碼是 `physics_simulator.py` 裡的 `baseColorFactor`（整件塗單一顏色）。

### 2. 從零開始學 UV 貼圖概念

用兩個比喻建立直覺：
- **剝橘子**：3D 是立體的，要攤平（剝皮攤開）才能在平面上對齊圖案，再「貼回去」
- **裁縫紙型**：跟做衣服的邏輯相反——衣服是先裁平面紙型再縫成立體；UV 展開是已經有立體服裝，
  反推它攤平後的樣子

核心概念：
- **UV 座標**：每個 3D 頂點除了 (x,y,z)，要多存一組 (u,v)，範圍 0~1，代表「對應到攤平後 2D 圖的哪個位置」
- **UV 展開（unwrapping）**：決定從哪裡「剪開」立體表面攤平成一塊或多塊平面
- **接縫（seam）**：剪開的地方，同一個 3D 位置在不同展開片需要不同 UV 值
- **渲染是自動的**：只要 GLB 帶了正確 UV+材質，Three.js 的 `GLTFLoader` 會自動畫出貼圖，
  真正花工的是「怎麼算出正確的 UV」跟「怎麼準備對齊的材質圖片」

也做了一個互動式示意圖（可點擊頂點看對應 UV 座標），幫助建立「一個 3D 頂點 ↔ 一組 2D 座標」的具體感覺。

**後來又寫了一版正式的技術文件版本**（拿掉比喻的口語敘事，改成技術報告寫法：問題定義 → 基本原理 →
UV 座標定義 → 五階段技術流程 → 結論），適合放進正式文件。

### 3. 盤點現有程式碼，確認真的完全沒有 UV

逐檔確認：
- `geometry_engine.py` 的 `_build_torso()` 只算 `vertices`(x,y,z) + `weights`(縮放用) + `faces`，無 UV 欄位
- `garment_processor.py` 的 `prepare()` 只做座標縮放，不碰材質
- `mesh_glb.py` 的 `export_glb()` 只餵 `vertices`+`faces` 給 trimesh，trimesh 給預設灰色
- `physics_simulator.py` 是唯一有「顏色」概念的地方，但只是塗單一色（`baseColorFactor`），
  而且只在 stub（mock）輸出裡用到，真實路徑甚至連這個都沒有
- Three.js 前端照單全收，沒 UV 沒貼圖，看到的就是灰色或單色

**結論：整條鏈路 UV 欄位從頭到尾不存在，不是哪裡寫錯，是壓根沒人加過這段邏輯。**

### 4. 設計「最小驗證原型」的範圍（不用真的分割照片）

三個關卡的設計，逐步討論定案：

**關卡一：怎麼判斷「正面」**
軀幹網格本來就是用角度算出來的（一圈一圈疊起來的橢圓形），所以直接用模型自己的 **Z 座標**
（`z >= 0.0`）判斷正不正面，跟照片完全無關，這一步連照片都還沒打開。

**關卡二：正面的點，UV 怎麼算**
「正交投影」——假裝從正前方拍照，直接拿頂點的 (x,y) 座標線性縮放到 0~1，z（深度）在這步不需要。

> **中途一個重要釐清**：一開始以為「z 不需要」代表 z 整個被丟掉，後來釐清 z 其實在另一條獨立路徑
> （渲染引擎算光影明暗，用完整 x,y,z 算法向量）繼續發揮作用，UV 貼圖（決定貼哪個顏色）跟光影明暗
> 是兩個獨立機制，最後結果兩者相乘疊加。

**關卡三：非正面的點怎麼處理**
沒有側背面照片，所以固定指向照片上同一個安全位置。

> **中途一個自己抓出來的錯誤並修正**：一開始想法是指向照片「背景角落」，但商品照片背景通常是白色，
> 藍色衣服的背面會顯示成白色，明顯不對。修正成指向照片「正中央」（衣服本身通常置中滿版，抓到的是
> 衣服的真實顏色，不是背景）。

### 5. 討論「要不要要求商家補拍三視圖」

結論：能解決問題（側背面也能有真實花紋），但代價是要改資料庫 schema（`Product.image_path` 現在是
單一欄位）、上架 API、前端表單，還要多處理接縫問題，工程量遠大於最小原型。**決定先用單張正面圖 +
安全色 fallback 驗證技術路徑，三視圖列為之後獨立評估的功能項。**

### 6. 第一天產出

- `reports/週誌_2026-08-31.md`（含以上內容的正式記錄）

## 第二天：實際動手做，寫程式碼驗證

### 1. 建立獨立驗證腳本

檔案：`3Dclothes_project/_uv_prototype_test.py`（前綴底線標記為暫存測試腳本，**完全沒有動到任何
生產程式碼**）。逐段教學走過一次：讀照片 → 讀模型（`_build_torso()`）→ `compute_uv()`（三關卡邏輯
寫成程式碼）→ `trimesh.Trimesh()` 包裝 → `TextureVisuals(uv, image)` 綁定 → `mesh.export()` 存檔。

過程中也把「XYZ 怎麼來的」往回追了兩層講清楚：`_build_torso()` 怎麼用 `T`（高度比例）跟 `THETA`
（角度）算出橢圓形圈圈，`T`/`THETA` 本身又是怎麼用 `np.arange()` + 除法 + `meshgrid` 生出來的。

中途也釐清一個誤解：「正面的點是不是從照片找的」——不是，分類正不正面完全只看模型自己的 Z 座標，
跟照片無關；照片是最後一步才登場，純粹當「查色表」用。

### 2. 第一次執行 + 除錯過程

**第一次跑**：用 `_build_torso()`（純數學軀幹）+ 條紋商品照片，輸出 glb 丟進自製的 Three.js 測試頁
（`_uv_prototype_viewer.html`，用本機 `http.server` + Browser Pane 檢視）。

**問題 1：畫面全黑/太暗，看不出貼圖** → 檢查材質才發現 trimesh 匯出的材質預設 `metalness=1`
（全金屬），沒有環境貼圖（HDR 反射）時幾乎不會顯示貼圖顏色本身。**修正**：手動設
`metallicFactor=0.0`。

**問題 2：換了修正後還是很單調看不出花紋** → 追查發現拿去測試的那張條紋照片，其實是**兩個模特兒的
拼接對比照**，不是乾淨的商品平拍圖，跟 catalog.json 寫的「pure white background, full garment flat
lay centered」提示詞對不上（AI 生圖沒有完全照提示詞跑出乾淨素材）。裁切照片重測後顏色有跟著變（棕色
系，因為裁到的區域皮膚較多），證實貼圖機制本身有在抓照片內容，只是這張照片不乾淨。

**改用業界標準棋盤格測試圖**（不依賴任何商品照片，高對比、每格顏色差異巨大，能立刻看出 UV
有沒有拉伸扭曲）。用 PIL 生成：8×8 格、6 種鮮豔色交錯黑色、外框+十字線+方向標記。

**問題 3：棋盤格貼出來整片綠色（十字線的顏色）** → 這是最關鍵的一個 bug。反覆用 Python 端獨立驗證
（matplotlib 畫出「正面頂點依 UV 抓到的實際顏色」散佈圖，跟 trimesh 讀回 glb 比對 UV/材質是否一致，
extract 出 glb 內嵌材質圖片比對）確認：**UV 計算邏輯、glb 匯出、材質嵌入全部正確**。真正原因是
**面的朝向（winding）反了**——三角形法向量指向內部，導致從外面看，看到的其實是「內壁」被貼上顏色，
外壁反而是culling掉看不到的那一面（貼圖在內壁，外壁沒東西可看，看起來像整片單一顏色）。

**修正嘗試**：`mesh.fix_normals()`。在**程序化生成的軀幹**（`_build_torso()`，頭尾開放、非封閉的
管狀網格）上測試，效果不明顯（使用者回報「沒變」）——推測 `fix_normals()` 仰賴封閉網格的體積判斷
邏輯，對開放管狀網格可能失效。

### 3. 使用者提出關鍵問題：「應該測試在現有模型上吧」

這是一個重要的路線修正。原本一直用 `_build_torso()`（純數學測試用軀幹）測試，但**真正商品上架
實際用的模型，走的是 `garment_processor.py` → `build_real_shirt_template()`，讀取一個真正做好的
`.obj` 檔案**（`geometry_physics/assets/garments/tshirt_base.obj`），不是純數學算出來的。

**改用真實商品模型重測**：讀取 `tshirt_base.obj`（7702 頂點、15180 面，比軀幹測試複雜很多），
一樣走三關卡 UV 邏輯 + `fix_normals()` + `metallicFactor=0`，重新匯出。

**結果：完全成功**——在獨立 Three.js 測試頁上看到完整的 T 恤形狀（含袖子），棋盤格正確顯示在外壁，
綠色外框線在袖口清楚可見，方塊比例沒有明顯扭曲。`fix_normals()` 在這個真實模型上確實修正成功
（跟軀幹測試的「沒變」不同，印證了「開放網格 vs 封閉網格」的推測）。

**也在真正的網站上驗證過一次**：用瀏覽器 F12 Console 動態 `import("/web_test/tryon.js")`，呼叫
網站正式程式碼的 `loadTryOnGlb()` 函式載入同一個檔案——證實不只是我們自己搭的測試頁能顯示，
網站正式的載入邏輯也完全吃得下這個修正過的檔案，不需要另外改前端程式碼。

### 4. 過程中意外發現的問題：`tshirt_base.obj` 來源不明

查了檔案本身（無作者/授權註解）、git log（只有一次性 initial commit）、團隊文件（只寫怎麼用，
沒寫哪裡來），都查不到這五個 `.obj` 服裝模型檔案（`tshirt_base`、`shirt_base`、`coat_base`、
`pants_base`、`shorts_base`）的真正來源。`geometry_engine.py` 裡 `build_real_shirt_template()`
的註解提到是為了讀外部資料集（例如 MGN Multi-Garment）設計的，但無法確認現有檔案是不是真的來自
該資料集，還是紀泓宇自己建模。**這是一個需要人去問清楚的待辦事項，不是技術問題。**

### 5. 第二天產出

- `3Dclothes_project/_uv_prototype_viewer.html`（獨立 Three.js 測試檢視頁）
